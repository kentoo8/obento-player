# Obento Player リファイン計画

## 目的

Obento Player の「動画を選ぶだけですぐ使える」という手軽さを維持しながら、変更しやすさ、動作の安定性、操作の分かりやすさを段階的に高める。

この計画では、次の制約を守る。

- `index.html` を直接開いて使える構成を維持する。
- 動画ファイルを外部へ送信しない。
- 既存の操作方法と保存済み設定を、意図なく変更しない。
- 大規模な書き換えを避け、各段階を単独で検証・リリース可能にする。

## 現状

### 強み

- インストールやサーバーなしで起動できる。
- 複数動画の表示、シャッフル、音声調整、回転、ピン留めなど、主要機能が一画面にまとまっている。
- 動画間の選択頻度を均等化するシャッフル方式を備えている。
- Blob URL の解放やメタデータの同時読み込み数制限など、ローカル動画を扱うための基本的な配慮がある。

### 改善余地

- `app.js` に状態、動画選択、音声、DOM生成、イベント処理が集中している。
- `style.css` が大きく、コンポーネント間の上書き関係を追いにくい。
- 自動テスト、静的解析、整形ルールがなく、変更時の回帰を検出しにくい。
- ドロップダウンなど一部のUIはキーボード操作や状態通知を改善できる。
- 読み込み失敗や対応形式の判定がコンソール中心で、利用者が原因を把握しにくい。
- 多数の動画・セルを扱う場合のCPU、メモリ、デコード負荷を定量的に確認できていない。

## リファインの原則

1. 先に現在の挙動をテストで固定し、その後に構造を変える。
2. 状態とDOM操作を分け、計算部分を副作用のない関数へ寄せる。
3. 見た目だけでなく、キーボード、スクリーンリーダー、狭い画面でも同じ操作を完了できるようにする。
4. エラーを握りつぶさず、利用者が次に取れる行動とともに表示する。
5. 性能改善は計測結果を基準に行う。

## 実施計画

進捗: Phase 1〜3 完了。Phase 4 実施中

### Phase 1: 品質の土台

目的は、以降の変更を安全に進められる状態を作ること。

- シャッフル、時間表示、設定値の正規化を純粋関数として切り出す。
- Node.js 標準テストランナーなど、依存を最小限にしたテスト環境を追加する。
- 公平な動画選択、シーン重複防止、候補不足、除外、設定境界値をテストする。
- JavaScriptとCSSの整形・静的チェック手順を定める。
- 手動確認項目をチェックリスト化する。

完了条件:

- 中核ロジックの正常系と境界ケースをコマンド一つで検証できる。
- READMEに開発・検証手順が記載されている。
- 現在の主要操作を確認する回帰チェックリストがある。

### Phase 2: JavaScriptの責務分離

目的は、機能追加時の影響範囲を限定すること。

- 状態と設定永続化をまとめる。
- シャッフルとシーン選択を独立したモジュールにする。
- 動画ファイル読み込み、メタデータ取得、Blob URL管理を分離する。
- 音声レベリングと再生制御を分離する。
- セル生成、表示更新、通知表示をUI層へまとめる。
- イベント登録を機能単位に整理し、重複する操作経路を共通コマンドへ集約する。

完了条件:

- 状態変更とDOM更新の入口が明確になっている。
- シャッフルや設定処理をDOMなしでテストできる。
- `file://` からの直接起動が引き続き機能する。

### Phase 3: UIとアクセシビリティ

目的は、初見・キーボード・支援技術の利用者にも操作状態が伝わるようにすること。

- ドロップダウンを適切なボタン、フォーカス管理、ARIA属性で操作可能にする。
- アイコンのみのボタンへ一貫したアクセシブル名と押下状態を付ける。
- フォーカス表示、Escによる閉じる操作、メニュー外クリックの挙動を統一する。
- 読み込み中、除外、再生失敗、非対応形式を画面内通知で伝える。
- 空状態とドラッグ＆ドロップ表示の日本語・英語混在を整理する。
- 画面幅だけでなく、タッチ操作と `prefers-reduced-motion` に対応する。

完了条件:

- マウスなしで主要操作を完了できる。
- 状態変化が見た目と支援技術の両方へ通知される。
- 主要な狭幅画面でコントロールが重ならない。

### Phase 4: 再生の堅牢性と性能

目的は、大量・長時間利用時にも破綻しにくくすること。

- メタデータ読み込みをキャンセル可能にし、リセット後の非同期完了を無効化する。
- 動画の読み込み失敗をセル単位で回復できるようにする。
- タイマー、イベントリスナー、AudioNode、Blob URLのライフサイクルを一元管理する。
- 非表示レイヤーのデコード、音声解析、DOM検索回数を計測して削減する。
- 動画本数・セル数別にCPU使用率、メモリ使用量、切替遅延を記録する。

完了条件:

- リセットや連続追加後に古い非同期処理が状態を書き換えない。
- 長時間再生でタイマーやメモリが継続的に増加しない。
- 性能改善の前後を同じ条件で比較できる。

### Phase 5: CSSと配布品質

目的は、デザイン変更と配布確認を容易にすること。

- CSSを基盤、レイアウト、コンポーネント、状態、レスポンシブの順に整理する。
- インラインスタイルをクラスへ移し、状態表現の命名を統一する。
- 色、余白、文字サイズ、重なり順をデザイントークンへ集約する。
- 外部フォントが取得できない環境でもレイアウトが崩れないことを確認する。
- 対応ブラウザとリリース前チェックを文書化する。

完了条件:

- UI部品の通常、ホバー、フォーカス、無効、選択状態が一箇所で追える。
- オフライン環境と対象ブラウザで起動・主要操作を確認できる。

## 優先順位

| 優先度 | 対象 | 理由 |
|---|---|---|
| P0 | Phase 1 | 回帰検出手段がないまま構造変更を進めるリスクを下げるため |
| P1 | Phase 2、Phase 4の非同期処理管理 | 保守性とリセット時の競合対策に直結するため |
| P2 | Phase 3 | 操作可能性とエラー理解を改善するため |
| P3 | Phase 4の性能計測、Phase 5 | 機能の土台を整えた後の方が安全に最適化できるため |

## 進め方

- 原則として、一つのコミットには一つの目的だけを含める。
- 構造変更とユーザーから見える変更を分ける。
- 各Phaseを始める前に対象範囲と手動確認項目を確定する。
- ユーザーから見える変更ではREADMEを同時に更新する。
- 各Phase完了時にこの文書の完了条件と優先順位を見直す。

## 今回の対象外

- サーバー必須の構成への移行
- 動画ファイルのアップロードやクラウド同期
- デスクトップアプリ化
- フレームワーク導入を前提とした全面的な書き換え

これらは、静的HTMLの制約では達成できない要件が具体化した時点で別途判断する。
